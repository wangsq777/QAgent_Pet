# QAgent Pet 产品转型方向文档

---

## 1. 背景

QAgent Pet 最初定位为「QQ 智能宠物伴侣 Agent」，主要设想是在 QQ 聊天场景中提供一个具备宠物人格、情绪感知、记忆与主动关怀能力的聊天宠物。

随着项目迭代，目前系统已经形成较完整的 Web 产品形态：

- 宠物选择与自定义宠物创建
- AI 对话与宠物人格 Prompt
- 亲密度成长
- 短期记忆、长期记忆与用户画像
- 情绪感知与情感需求细化规划
- 日程提醒与主动关怀
- 宠物串门
- 陪你学 GitHub 开源项目
- Web 端聊天页、记忆面板、学习页等完整前端交互

当前实现已经不再只是一个 QQ 聊天 Bot 的雏形，而更接近一个独立的 AI 宠物产品。继续仅围绕 QQ 内部聊天场景推进，会面临产品表达受限、差异化不足和现有 Web 前端价值被弱化的问题。

因此，产品方向需要从「QQ 内部聊天宠物」拓展为更完整的「个人 AI 电子宠物伴侣」。

---

## 2. 当前方向存在的问题

### 2.1 QQ Bot 形态承载能力有限

如果继续只按 QQ 接入方式推进，用户最终看到的主要体验会退化为聊天窗口中的一问一答：

```text
用户：今天好累
宠物：主人辛苦啦，我陪着你！
```

这种体验难以充分展示当前项目已有的多项能力：

- 宠物选择页
- 自定义宠物创建流程
- 记忆面板
- 亲密度可视化
- 串门面板
- 陪我学页面
- 情绪陪伴细节
- 宠物状态变化

QQ 消息流更适合轻量对话，不适合承载复杂的宠物养成、状态展示、学习陪伴和多面板交互。

### 2.2 与通用 AI 助手差异化不足

如果 QAgent Pet 仅以 QQ 聊天 Bot 的形式存在，用户很容易将其理解为「一个有宠物语气的 AI 聊天机器人」。

在这种场景下，产品会自然进入豆包、Kimi、通义等通用 AI 助手的竞争区间。但 QAgent Pet 不适合与这些产品比拼：

- 通用问答能力
- 搜索能力
- 写作能力
- 办公效率
- 专业知识覆盖

QAgent Pet 的优势不在于「更聪明的工具」，而在于「更有陪伴感的关系型 AI 宠物」。

### 2.3 现有 Web 前端与 QQ 使用形态割裂

当前项目已经实现了完整 Web 端：用户打开网页，选择宠物，进入聊天页，查看记忆面板，使用学习功能。

而 QQ Bot 的用户路径是：用户在 QQ 中发送消息，后端通过平台回调生成回复，用户主要停留在 QQ 消息窗口内。

两种形态差异明显：

| 维度 | 当前 Web 端 | QQ Bot 端 |
|------|-------------|-----------|
| 入口 | 浏览器页面 | QQ 聊天窗口 |
| 主要交互 | 页面、按钮、面板、聊天 | 文本消息 |
| 宠物展示 | 卡片、头像、状态、面板 | 文本昵称/头像 |
| 自定义宠物 | 可做完整配置流程 | 交互复杂 |
| 记忆面板 | 可视化展示 | 难以自然展示 |
| 学习功能 | 可承载长内容和章节 | 消息流过长 |
| 主动关怀 | 可结合 UI 展示 | 受平台限制 |

如果继续以 QQ 为唯一主线，现有 Web 前端会变成辅助配置后台，核心用户体验反而回到简单聊天窗口，投入产出不理想。

---

## 3. 产品转型结论

产品路线调整为：

> 保留现有 Web 端形态，并在此基础上加入桌宠方向，将 QAgent Pet 从「QQ 内部聊天宠物」拓展为「个人 AI 电子宠物伴侣」。

新的产品主线：

```text
个人 AI 电子宠物伴侣
```

当前入口：

```text
Web 端完整功能中心
```

下一阶段重点入口：

```text
桌宠端常驻陪伴入口
```

远期扩展入口：

```text
QQ / IM / 移动端等多端入口
```

QQ 不再作为唯一主入口，而是未来可选接入渠道之一。

---

## 4. 新产品定位

### 4.1 推荐定位

> QAgent Pet 是一个个人 AI 电子宠物伴侣。它拥有可自定义的宠物人格、长期记忆、情绪理解、主动关怀和学习陪伴能力，可以通过 Web 端完整交互，也可以逐步拓展为桌面常驻宠物，陪伴用户的学习、生活和情绪状态。

### 4.2 简短版本

> 一个会记住你、陪你学习和生活、常驻在身边的 AI 电子宠物。

### 4.3 与原定位的关系

原定位：

```text
QQ 智能宠物伴侣 Agent
```

新定位：

```text
个人 AI 电子宠物伴侣
```

定位变化不是完全推翻原方向，而是从单一 QQ 场景扩展为更通用的个人陪伴型产品。

---

## 5. 产品架构方向

未来产品可以拆分为「核心服务 + 多客户端入口」：

```text
QAgent Pet Core
AI 对话 / 宠物人格 / 记忆 / 亲密度 / 日程 / 情绪理解 / 学习陪伴
        │
        ├── Web 端：完整功能中心
        │     ├── 宠物选择
        │     ├── 自定义宠物
        │     ├── 完整聊天
        │     ├── 记忆面板
        │     ├── 用户画像
        │     ├── 陪我学
        │     ├── 串门功能
        │     └── 设置与管理
        │
        ├── 桌宠端：常驻陪伴入口
        │     ├── 透明置顶宠物
        │     ├── 气泡聊天
        │     ├── 主动提醒
        │     ├── 动画状态
        │     ├── 托盘菜单
        │     └── 快速打开 Web 完整面板
        │
        └── QQ / IM 入口：远期扩展
              ├── 消息对话
              ├── 简化提醒
              └── 多端同步入口
```

这种架构可以最大程度复用已有后端能力，同时避免产品被单一平台限制。

---

## 6. Web 端定位

Web 端继续保留，并成为 QAgent Pet 的完整功能中心。

### 6.1 Web 端职责

Web 端适合承载复杂、完整、可配置的功能：

1. 宠物选择
2. 自定义宠物创建与编辑
3. 完整聊天记录
4. 记忆面板
5. 用户画像编辑
6. 陪我学 GitHub 项目
7. 宠物串门
8. 设置中心
9. 数据管理
10. 桌宠偏好配置

### 6.2 Web 端后续调整方向

Web 端不应只表现为普通聊天网页，而应逐步强化「电子宠物」概念：

- 增加宠物状态展示
- 增加宠物轻动画
- 增加轻养成元素
- 增加今日陪伴、今日互动等信息
- 增加桌宠模式入口或预览
- 将学习、记忆、画像等功能包装为宠物成长的一部分

---

## 7. 桌宠端定位

桌宠端不是替代 Web 端，而是新增一个日常陪伴入口。

### 7.1 桌宠端职责

桌宠端负责提供「存在感」和「轻量互动」：

1. 常驻桌面
2. 轻量聊天
3. 主动气泡提醒
4. 情绪/状态动画
5. 日程提醒
6. 久坐/喝水/睡觉提醒
7. 宠物状态展示
8. 快速打开完整 Web 面板

### 7.2 桌宠端不应承载的内容

桌宠窗口应保持轻量，不适合塞入过重功能：

- 完整学习长文
- 大型记忆面板
- 复杂画像编辑
- 复杂自定义宠物表单
- 大量历史消息管理

这些内容应由 Web 端或完整窗口承载。

---

## 8. 与豆包等通用 AI 的差异化

QAgent Pet 不应与豆包等通用 AI 助手正面竞争「更强问答」或「更高效率」。

新的差异化方向是：

> 豆包是工具型 AI 助手，QAgent Pet 是关系型 AI 电子宠物。

### 8.1 差异化重点

| 差异点 | 通用 AI 助手 | QAgent Pet |
|--------|--------------|------------|
| 核心价值 | 解决问题、提升效率 | 长期陪伴、关系成长 |
| 交互方式 | 用户主动提问 | 宠物可主动关心 |
| 角色感 | 弱，可临时扮演 | 强，持续人格与状态 |
| 记忆价值 | 多为效率辅助 | 形成关系连续性 |
| 情绪陪伴 | 功能之一 | 核心能力之一 |
| 存在形态 | App / 网页 / 对话框 | Web + 桌宠常驻 |
| 成长感 | 弱 | 亲密度、状态、动作、记忆 |

### 8.2 产品表达重点

QAgent Pet 的优势应表达为：

- 它会记住你
- 它有自己的性格
- 它会和你建立关系
- 它能主动关心你
- 它可以陪你学习和生活
- 它不是万能工具，而是一只长期陪伴你的电子宠物

## 9. 后续新增需求方向

转型为个人电子宠物后，新增需求空间明显扩大。

### 9.1 桌宠基础能力

- 透明置顶窗口
- 无边框窗口
- 可拖拽移动
- 点击互动
- 右键菜单
- 系统托盘
- 开机自启
- 窗口位置记忆
- 勿扰模式
- 桌面通知

### 9.2 宠物状态系统

可新增更适合电子宠物的状态：

| 状态 | 说明 |
|------|------|
| idle | 正常待机 |
| happy | 开心 |
| lonely | 很久没互动，想你 |
| sleepy | 夜间困困 |
| focused | 陪你学习 |
| comforting | 安慰你 |
| reminding | 提醒你 |
| hiding | 躲起来 |
| excited | 兴奋 |

### 9.3 宠物动画与表现

- 待机动画
- 眨眼动画
- 呼吸动画
- 思考动画
- 说话动画
- 开心跳动
- 睡觉动画
- 提醒动画
- 被拖动动画
- 陪学动画
- 亲密度解锁动作

MVP 阶段可以先使用图片 + CSS 动画，不必一开始引入复杂 Live2D。

### 9.4 轻养成系统

在现有亲密度基础上，可加入轻量养成元素：

- 今日互动次数
- 今日陪伴时长
- 连续陪伴天数
- 宠物心情
- 宠物精力
- 解锁称呼
- 解锁动作
- 解锁日常台词

重点不是做复杂数值游戏，而是强化关系感。

### 9.5 主动陪伴系统

基于现有主动关怀能力扩展：

- 早安问候
- 晚安提醒
- 久坐提醒
- 喝水提醒
- 长时间未互动提醒
- 日程提醒
- 学习计划提醒
- 情绪低落后的二次关怀
- 节日问候
- 生日/纪念日提醒

### 9.6 情绪陪伴系统

结合后续情感捕捉细化规划，将情绪理解用于宠物行为与回复策略，而不是直接展示标签：

- 用户焦虑时，宠物进入安抚状态
- 用户低落时，宠物减少说教，更多陪伴
- 用户开心时，宠物一起庆祝
- 用户疲惫时，宠物提醒休息
- 用户需要建议时，宠物给简短可执行步骤
- 用户只想倾诉时，宠物少建议、多接住情绪

### 9.7 陪学系统桌宠化

现有「陪你学 GitHub 开源项目」功能可以成为桌宠差异化能力：

- 桌宠进入陪读模式
- 学习时宠物在桌面角落陪伴
- 完成章节后宠物庆祝
- 长时间未继续学习时宠物提醒
- 学习进度影响亲密度
- 宠物总结今日学习成果

### 9.8 宠物串门桌宠化

现有串门功能可以进一步桌宠化：

- 两只宠物在桌面气泡中对话
- 宠物之间讨论用户最近状态
- 宠物互相吐槽或鼓励
- 用户可以插话
- 串门结束后形成共同记忆

## 10. 推荐实施路线

### Phase 1：产品定位调整

目标：统一产品叙事，不大规模修改代码。

任务：

1. README 和需求文档中将主定位从「QQ 智能宠物伴侣」调整为「个人 AI 电子宠物伴侣」。
2. 明确 QQ 是远期可选入口，不再是唯一主线。
3. 明确 Web 端是完整功能中心。
4. 明确桌宠端是下一阶段常驻陪伴入口。
5. 保留现有后端核心能力，不推翻重做。

### Phase 2：Web 端电子宠物化

目标：在 Web 端先强化电子宠物产品感。

任务：

1. 增加宠物状态展示。
2. 增加简单宠物动画。
3. 增加轻养成信息。
4. 增加桌宠模式入口或预览。
5. 优化文案，从「聊天 AI」转为「电子宠物陪伴」。

### Phase 3：桌宠 MVP

目标：验证桌宠方向可行性。

任务：

1. 选择桌面壳技术，优先考虑 Electron 或 Tauri。
2. 新增透明无边框置顶窗口。
3. 宠物支持拖拽移动。
4. 点击宠物弹出聊天气泡。
5. 输入消息后调用现有聊天 API。
6. 等待 LLM 时显示思考状态。
7. 回复时显示气泡。
8. 主动关怀时弹出桌面气泡。
9. 右键菜单支持打开完整 Web 面板。
10. 支持关闭到托盘。

### Phase 4：桌宠体验增强

目标：让桌宠更像长期使用的产品。

任务：

1. 系统托盘完善。
2. 开机自启。
3. 勿扰模式。
4. 桌面通知隐私设置。
5. 窗口位置记忆。
6. 多宠物切换。
7. 宠物状态动画增强。
8. 久坐、喝水、睡觉提醒。
9. 学习陪伴状态。
10. 本地数据备份与恢复。

## 11. 技术路线建议

### 11.1 保留现有后端

现有 FastAPI 后端继续作为 QAgent Pet Core：

- AI 对话
- 记忆服务
- 情绪理解
- 用户画像
- 日程提醒
- 学习服务
- 串门服务
- 自定义宠物

不建议为了桌宠重写后端。

### 11.2 新增桌宠专用前端入口

建议在现有 `frontend/` 下新增桌宠专用页面，例如：

```text
frontend/desktop_pet.html
frontend/css/desktop_pet.css
frontend/js/desktop_pet.js
```

桌宠页面只负责轻量常驻互动，复杂功能仍跳转到现有 Web 页面。

### 11.3 桌面壳选择

候选方案：

| 方案 | 优点 | 缺点 | 建议 |
|------|------|------|------|
| Electron | 成熟、资料多、透明窗口/托盘/通知好做 | 包体较大、内存占用较高 | 适合 MVP 快速验证 |
| Tauri | 包体小、性能好 | 桌面能力细节调试成本略高 | 适合后续轻量产品化 |
| PySide/PyQt | 与 Python 后端心智统一 | Web 复用和现代 UI 成本较高 | 可选但不优先 |

MVP 阶段推荐优先 Electron。

### 11.4 后端启动与数据目录

桌宠应用需要解决：

1. 桌面应用启动时自动启动后端。
2. 检查端口是否被占用。
3. 后端启动失败时给出友好提示。
4. 应用退出时决定是否关闭后端。
5. 打包后 Python 环境和依赖如何分发。
6. SQLite 数据库应迁移到用户应用数据目录。

推荐后续将数据库路径从项目根目录迁移到用户数据目录，例如：

```text
Windows: %APPDATA%/QAgentPet/qagent_pet.db
macOS: ~/Library/Application Support/QAgentPet/qagent_pet.db
Linux: ~/.local/share/QAgentPet/qagent_pet.db
```

## 12. 阶段性结论

当前沟通形成的产品方向为：

> QAgent Pet 不再只作为 QQ 内部聊天宠物推进，而是升级为个人 AI 电子宠物伴侣。现有 Web 端继续保留，作为完整功能中心；后续新增桌宠端，作为常驻桌面的轻量陪伴入口；QQ / IM 接入作为远期可选扩展。

这一路线的优势：

1. 不浪费当前 Web 端和后端成果。
2. 能更好承载宠物人格、记忆、亲密度、学习和串门等已有能力。
3. 能与豆包等通用 AI 助手形成差异化。
4. 能继续扩展大量自然的新需求。
5. 产品叙事更统一，从「聊天 Bot」升级为「长期陪伴型电子宠物」。

后续优先建议：

1. 更新项目定位文档与 README。
2. 为 Web 端补充电子宠物化设计。
3. 制定桌宠 MVP 技术方案。
4. 逐步实现桌宠入口，而不是一次性推翻现有系统。
